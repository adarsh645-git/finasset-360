# Map: FinAsset 360 spec

## Destination

A full product spec (features, data model, UI structure, tech stack) for a deployed, multi-tenant personal net-worth web app (FinAsset 360) — free-tier hosted (Vercel + Supabase), Google sign-in with open signup, each user isolated via Postgres Row-Level Security — detailed enough to hand to an implementation session to build from scratch. Hard-to-reverse calls are recorded separately as ADRs (see `docs/adr/`).

### Settled foundation (treat as given — don't re-litigate in a ticket)

- **Stack**: Next.js, single combined app (frontend + API routes, no separate backend service), deployed to Vercel. Supabase for Postgres storage + Google Auth. See ADR 0002.
- **Multi-tenancy**: open Google sign-up, no invite gating, no admin dashboard for v1. Isolation enforced via Postgres Row-Level Security scoped to `auth.uid()`. See ADR 0001.
- **Asset Class / Liability Class**: ship global sensible defaults; each User can also add their own custom classes.
- **Currency**: open ISO-currency-code picker per Holding/Liability (not a hardcoded list); one configurable display/home currency for aggregate views (Net Worth, distribution chart); FX rate is stored alongside each Valuation at the time it's recorded, and historical views use that stored rate, not today's.
- **Granularity**: periodic Valuation snapshots only — no transaction ledger, no cost basis, no capital-gains tracking. See ADR 0003.
- **Valuation automation**: stocks/ETFs — Finnhub (60 calls/min free). Gold/metals — Metals.Dev primary, MetalpriceAPI fallback (~100 free requests/month each; Metals-API.com has no free tier despite earlier assumption). Real estate — manual periodic entry only, no automated home-value lookup. **Required**: one shared, server-side cached fetch (e.g. a cron-updated Supabase table) serving all tenants — free-tier limits don't survive per-tenant polling.
- **Valuation entry**: every Holding without a `price_lookup_symbol` is valued by the user typing the number in. No research-prompt feature, no LLM assistance of any kind in v1 (cut 2026-09-08, see Out of scope).
- **Planning features**: **Target Allocation** (goal % per Asset Class vs. actual), **Projection**, and a **Target Net Worth** with a required-contribution solve are in scope for v1. Still single-scenario — one growth rate, one escalation rate, one inflation rate, no named alternatives. Contribution is a **single typed monthly amount** plus an optional annual escalation rate (default 0); an itemized line list was considered and rejected.
- **Inflation**: settled. The projection computes entirely in **nominal** terms (all rates quoted nominal; a loan's rate is contractually nominal), then deflates for display using one expected-inflation assumption. Both the nominal and inflation-adjusted lines are charted, forking at today. Real is the primary line — headline, Target comparison and solver all read from it.

## Decisions so far

- [Which free-tier market-data API(s) to use](issues/01-market-data-api-research.md): Finnhub for stocks/ETFs, Metals.Dev (fallback MetalpriceAPI) for gold — both require a shared server-side price cache, not per-tenant polling.
- [Provision Vercel account](issues/06-provision-vercel.md): Vercel account already exists (free/hobby tier), ready to connect to this repo whenever a build ticket is ready to deploy.
- [Data-model schema](issues/03-data-model-schema.md): full Postgres/Supabase schema settled — `portfolio.user_id` as the single per-user anchor (no separate `users` table), flat `user_id` RLS on every tenant table, two separate Valuation tables, a non-RLS'd `price_cache` refreshed by a once-daily Vercel Cron Job, and `archived_at` (not hard delete) on Holding/Liability to keep portfolio-distribution-over-time accurate after a sale. Amended by the Projection-method ticket with new optional loan-amortization fields on `liability`.
- [Projection method](issues/04-projection-method.md): flat annual growth rate + monthly contribution applied portfolio-wide (or to a single Holding), year-by-year trajectory via standard monthly-compounding FV-with-annuity formula; Liabilities held flat by default, or auto-amortized via a closed-form payoff formula when optional loan fields (rate, original amount, term, optional custom payment, optional extra payment) are set — capability-based, not Mortgage-Class-specific; a Liability can link to the Holding it financed for a combined "Projected Net Position" view.
- [Projection formula reconciliation](issues/07-projection-formula-reconciliation.md): the Projection projects **Holdings total** forward and subtracts each Liability projected on its own rule — it never grows a netted Net Worth figure (which had implicitly compounded every debt at the Portfolio's growth rate, making Amortization Assumptions decorative). When a loan pays off, its freed payment (less any escrow portion) is added to the monthly contribution, so `C` is piecewise-constant and the projection is a chain of closed-form segments. Amended the Projection-method and Data-model tickets in place.
- [App UX shape prototype](issues/08-app-ux-shape-prototype.md): the **Balance Sheet** page shape was rejected on reaction (2026-09-07). UX-shape question reopened at the Tree-UI prototype ticket below. Carried forward: Check-in mode, inline click-to-edit Valuation, Live Estimate "use" action, a separate Plan page, Archive as a detail-panel action (research-prompt-with-copy was carried forward here too, then cut 2026-09-08 — see Out of scope), and the session-rhythm facts (monthly check-in over 10–30 Valuations plus several distribution-only visits; desktop-first, phone needs only "read Net Worth" + "record one Valuation").

- [Tree-UI prototype](issues/02-tree-ui-prototype.md): **Variant E** — Miller-column navigation (~270px columns, breadcrumb, rightmost column is the detail panel; Portfolio and Plan as the two roots) carrying the dashboard/detail information set: Net Worth headline + recorded/projected timeline, Target Allocation bars with target tick and money gap, staleness list, Liabilities as their own branch with Projected Net Position on both sides of a link. Inline click-to-edit Valuation with backdating, Live Estimate "use", and a guided Check-in mode. Two-column dashboard above ~1200px. Near-monochrome, one slate accent, 15px base, plus one minimal single-stroke icon per Asset/Liability Class (overriding D's no-icons rule; custom classes need a fallback glyph).

- [Narrow-viewport behavior](issues/10-narrow-viewport-behavior.md): below **900px** (the column shell's 830px floor plus margin) Miller columns are replaced by an **accordion outline** — expand-in-place tree, detail as a bottom sheet — ordered Net Worth + timeline, then the outline, then Target Allocation/staleness/Check-in. Two navigation models across widths is a deliberate call, not an accident. Measurement showed the top strip, Check-in mode, dashboard content and the Plan page were already narrow-capable; the whole problem was the shell's 830px floor. Also settles app-wide touch affordances (persistent edit affordance, Check-in tap targets, 44px rows, sticky Net Worth).

- [Target Net Worth](issues/11-target-net-worth.md): one Target per User, naming an **amount and a date** together, stated in today's purchasing power. The projection computes nominal and is deflated for display; **both lines are charted**, forking at today (history stays nominal — deflating it would need real CPI). A real growth rate was rejected because a loan's rate is contractually nominal and cannot be converted. Gap reads as a date first, then a figure; a passed target date prompts for a new one.

- [Itemized contributions](issues/12-itemized-contributions.md): itemization **rejected** — the seeded line list presumed employment, kind tags computed nothing, and per-line escalation proved redundant (a single 2.9% global rate reproduces a half-at-5%/half-flat mix). Its one real job, prompting for a forgotten employer match (9%), is served by helper text on one field. The scalar stays; **one `contribution_escalation_rate` field, default 0**, is added — the largest single input measured (+27% at 5%). Segmented closed form verified against simulation to 1×10⁻⁷ across 21 segments.

- [Required-contribution solver](issues/13-required-contribution-solver.md): solves for the **starting contribution** (escalation held as an input; the achievable date comes free from the gap display). Confirmed linear, so one subtract and one divide, no iteration. Correction it forced: against the real line the required contribution is ~**2.6× the nominal figure** — 16,893/mo, not 6,425/mo, for 6M by 2046. Never mathematically unreachable, so no threshold: the figure is always paired with the achievable date. Negative results are shown as withdrawal capacity, escalation and all. Derived, never stored.

- [Build spec](issues/14-build-v1.md): the planning arc's synthesis — [`docs/SPEC.md`](../../docs/SPEC.md), a full v1 build spec (problem, solution, 119 user stories, implementation decisions, testing decisions, out of scope). Two test seams settled with the user: the **projection engine as a pure function** (ticket 12's month-by-month simulation and ticket 13's linearity check become the oracles) and the **HTTP route boundary against a real Postgres with RLS enabled and two Users** (not lowered to mocked repositories — that would test none of the RLS policies). UI verified by hand at the user's own viewport.

## Not yet specified

- Data export/import.
- Whether a single portfolio-wide growth rate is enough. Settled foundation says one flat rate, no per-Asset-Class rates — but the Reading-2 projection now grows each Holding explicitly, which makes the consequence visible: the sample house compounds to 2,052,327 over 20 years at the same 6% as the equities. Not reopened here; flagged as the place someone will push back.
- UI-level affordances around Valuation **corrections** and **unarchiving** — the UI ticket settled backdating on inline edit and an Archive action in the detail panel, but not an unarchive path or any edit-history display, beyond the schema-level rule from the data-model ticket (same-day edits overwrite the existing row; "removing" a Holding archives rather than deletes it).
- Reminders/notifications to prompt periodic valuation updates. (Check-in mode and the staleness list now cover the in-app nudge; this fog is only about *out-of-app* reminders.)
- Whether a Projection should show what happens when the assumptions are wrong. **Four** assumptions now compound over the horizon — growth rate, contribution escalation, full reinvestment of freed loan payments, and inflation. Charting the nominal and real lines together (from [Target Net Worth](issues/11-target-net-worth.md)) addresses the inflation one by making it visible; the other three are still stated once and never stress-tested. Not a multi-scenario feature (ruled out), but possibly a single downside line or a stated sensitivity.
- Whether the Plan page still holds together. [Tree-UI prototype](issues/02-tree-ui-prototype.md) settled it as a single page when it carried a growth rate, a contribution and a horizon. It now also carries an escalation rate, an inflation rate, a target amount and a target date as inputs, and a required contribution, a gap date, a gap figure and two charted lines as outputs. That may need sectioning or a second page; nobody has looked at it since the inputs doubled.
- Empty and first-run states: what the Portfolio looks like with no Asset Classes, no Holdings, and no Valuation history — every prototype so far has been populated with fictional data.

## Out of scope

- **A compensation model** — entering base salary, bonus, stock compensation, employer match percentages, ESPP, other benefits, and a blended tax rate, to *derive* the savings figure. Ruled out at charting on measurement, not taste: RSU vest lumpiness is worth 0.99% over 20 years, and a user-guessed blended tax rate swings the result by 5% — so the derived number is less reliable than a typed one while looking more authoritative, and it goes stale silently on every raise. The one thing it genuinely bought (catching a forgotten 401k match, worth 9%) is delivered far more cheaply by helper text on the single contribution field (see [Itemized contributions](issues/12-itemized-contributions.md), which rejected the line list too), and contribution growth — the input that really matters, worth 27% — is one escalation field that needs no salary at all. Also keeps ADR 0003's "not a tax tool" line intact by never needing an expense or tax model. Returns only if the destination is redrawn toward a compensation planner (e.g. "can I afford to raise my 401k?"), which is a different product.

- **An LLM research-prompt feature** — a copyable, per-Asset-Class prompt in the Holding detail panel, and the deeper version the user actually wanted: moats, competitors, sector position. Ruled out at [Research-prompt templates](issues/09-research-prompt-templates.md) (2026-09-08) after drafting the prompts concretely, which split them cleanly. The Real Estate and Crypto drafts answer *"what is this worth"* — the tracker's question, but a thin wrapper around a number the user is about to type in anyway. The Equity draft answers *"should I own this"* — moats, bear cases, relative market share — and **nothing it returns is a Valuation**; its output fits no field in the schema. So the prompt worth writing is the one this app can't use, and the ones it could use don't earn a feature. The ticket's per-Asset-Class premise didn't survive drafting either: the good prompt is Equity-shaped and doesn't generalize (Real Estate wants comps, Crypto a spot price, Cash silence, Precious Metal is already live-priced). The cut also removes an `asset_class` template column, the custom-class fallback problem, and the global-defaults editability problem (RLS grants `UPDATE` only where `owner_id = auth.uid()`; global defaults are `owner_id IS NULL`, so shipped templates could never have been user-edited without copy-on-write invented for this feature alone). The user's own read: "worth pursuing but it does not belong in this app." Returns as **its own effort** — an investment-research product, not a net-worth tracker — with the four drafts preserved verbatim in the closed ticket. Keeping it out also holds ADR 0003's line: this app records what things are worth, it does not reason about whether to own them.
