# Variant E — design brief

Design brief only. No code. Target: add `?variant=E` to `prototypes/tree-ui/index.html`, following the pattern of `renderC`/`renderD` (own DOM-builder functions, sharing only `DATA`/`DERIVED`/the math+format helpers/`onActivate` with the other variants — see lines 340–599 for what's shared).

## 1. The shape, and how the synthesis was resolved

E is Variant C's Finder shell — fixed-width list columns that drill left to right, a clickable breadcrumb, the rightmost column always the detail panel for whatever is selected — carrying Variant D's dashboard/detail content instead of C's thinner originals, plus the four salvaged interactions from the rejected Balance Sheet ticket. Three real frictions had to be resolved to make this one coherent shape rather than a collage:

**Where the dashboard lives without a sidebar to anchor it.** C already answers this by construction: column 1 (Asset Classes + Liabilities) is always the leftmost column, and when nothing is drilled into (`path = []`), the rightmost column *is* the dashboard. That's the root/dashboard column — D's Net Worth headline, timeline, allocation bars and staleness list simply move into that existing slot. What C's shape loses that D's sidebar had for free is a permanent view of the Net Worth figure while deep in a column stack — D's sidebar kept the "Portfolio" row with its total on screen at all times; Miller columns scroll column 1 out of view as you drill. E compensates with a persistent top strip (wordmark row) that always shows a compact Net Worth readout, independent of drill depth, and is itself a click target back to the dashboard — a one-line global anchor, not a sidebar, so it doesn't reintroduce the thing that was explicitly rejected. Staleness has the same problem one level down: D's tree shows every stale leaf at a glance because the whole tree is always rendered; C's columns only ever show one level's children at a time, so a stale Holding three levels deep is invisible until you drill to it. E resolves this the same way D already half-solved it for the dashboard: the quiet staleness list on the dashboard column is the comprehensive, always-reachable index of every stale item (click-through works from any depth via the breadcrumb's "Portfolio" root), and Asset-Class/Liability-Class rows in column 1 additionally carry a small quiet marker when they contain a stale descendant, so the gap doesn't need drilling to notice.

**Check-in mode was built for one scrolling sheet.** It does not get wedged into the column browser as a "visit every row across every open column" mode — that would require every column to be open simultaneously, which contradicts Miller navigation entirely. Instead, entering Check-in suspends column browsing altogether: the whole content area (columns and detail column both) is replaced by a single full-width card showing one Holding at a time, linear queue instead of spatial tree. This is a deliberate, temporary regression to "one sheet" for the duration of the mode, because the two are different mental modes (browsing a hierarchy vs. running a fixed checklist) and Miller columns have no natural way to represent "currently on item 12 of 27" spatially. Check-in is reachable from the persistent top strip, not from inside the tree, so it doesn't depend on where you were browsing when you started it.

**Where Plan sits relative to the breadcrumb.** "Reachable from the breadcrumb root" is read literally: Plan becomes a second root, a sibling of Portfolio at breadcrumb depth 0, not a page nested under Portfolio and not a modal. The top strip shows both root destinations as plain text links (`Portfolio` / `Plan`); whichever is active is the breadcrumb's first segment. Plan has no column children of its own — it's a single page (allocation editor, then assumptions, then a read-only timeline preview), so the breadcrumb never grows past one segment while inside it.

One more resolution worth stating up front because it shapes several later sections: the salvaged inline click-to-edit Valuation was designed for a balance-sheet row (full-width, room for a value cell and a date affordance side by side). A 220px-wide column row has neither the room nor a safe way to distinguish "click to edit" from "click to drill" — row clicks in columns 1–3 already mean "select/drill." So inline edit lives only on the detail column's headline figure (the one place a value is shown at full size, on its own, with nothing to disambiguate against). This is covered in full in §5 and called out again in §7.

## 2. Column-by-column breakdown

Reuse C's structure: **column 1** = Asset Classes + Liabilities (root list, always present), **column 2** = Holdings of a selected Asset Class, or Liability Classes of Liabilities, **column 3** = Liabilities of a selected Liability Class (only appears on the Liabilities branch — the Asset side is only two list-columns deep, because a Holding is a leaf whose "children" are its own detail, not another column). **Detail column** is always the rightmost, showing content for whatever the deepest path segment resolves to, including the empty path (dashboard).

List columns keep C's row shape (`c-row`: label left, money right, chevron if it has children) and 220px fixed width. Raise the detail column's minimum width from C's 360px to ~440px — D's timeline and allocation bars need more room to breathe than C's plain detail rows did.

**Column 1 — root list.** Same as C's `cBuildCol1`: Asset Classes in fixed data order, a gap, then "Liabilities" as its own row (own top-level branch, mirroring Asset Class ↔ Liability Class, matching both C and D — not folded under anything). Per-row treatment: money figure only, no per-class staleness dimming (dimming is a leaf-level signal — see column 2/3), but append a small quiet marker (a muted `·` after the class name, e.g. "Equity ·") when that class contains at least one Holding/Liability older than 30 days, with a `title` tooltip stating the count. The marker is part of the label, not a separate click target — clicking anywhere in the row still drills, as normal.

**Column 2 — Holdings, or Liability Classes.** When column 1's selection is an Asset Class: one row per Holding, label + `fmtMoney(valuation)`, no chevron (Holding is a leaf — clicking it selects it into the detail column directly, no column 3 on this branch). The money figure is rendered in `--text-muted` (dimmed) when `dIsStale`-equivalent (>30 days since `recordedAt`) — this is D's staleness-dimming rule, reused verbatim, applied to the value text itself rather than a separate glyph. No Live Estimate indicator at this level (see §7 — that content stays in the detail column, per the source spec's own wording "hint under the value").
When column 1's selection is Liabilities: one row per Liability Class, chevron (has children — column 3), money as negative `fmtMoney` in `--liability` color, no staleness dimming at this aggregate level (same reasoning as column 1).

**Column 3 — Liabilities within a Liability Class.** One row per Liability, label + negative `fmtMoney(balance)` in `--liability` color, staleness dimming on the value exactly as column 2's Holdings. No chevron (leaf).

**Detail column** — content by selection:

- *Path empty (dashboard):* (1) Net Worth headline "Holdings − Liabilities · as of [date]" exactly as D's `dRenderPortfolioView`. (2) The joined recorded/projected timeline (D's `dBuildTimeline`, reused as-is: solid recorded line, dashed projected line, Today seam, mortgage-payoff marker, year-20 endpoint label, hover readout). (3) Target Allocation vs actual as horizontal bars in **tree order** (not sorted by |Δ|, unlike C's original table) with a target tick and the money gap line underneath each bar ("257,155 below target"), reusing `dBuildAllocRow`/`dAllocGapText`. (4) The quiet staleness list ("Valuations older than 30 days"), each item clickable — clicking sets the column path to that item's Asset Class/Liability Class and selects the leaf, same as D's `dSelect` but driving the Miller `path` state instead. (5) A "Start Check-in" text button at the foot of the dashboard column, in addition to the top-strip entry point (§3) — a convenience shortcut, not a second mechanism.

- *Asset Class selected (path length 1):* class total, share of Holdings, target %, gap text, one allocation bar row (reuse `dBuildAllocRow` with `showName:false`), then a Holdings table with columns Holding · Valuation (dimmed if stale) · As of · Live Estimate — same shape as C's `cBuildClassView`/D's `dRenderClassView`. This table isn't pure redundancy with column 2: it adds the As-of date and Live Estimate columns that don't fit in a 220px row.

- *Holding selected (path length 2):* headline valuation (inline-editable — see §5), as-of line with staleness note when >30 days, Live Estimate hint ("+2.3% vs last Valuation · not a Valuation until you record it") plus a "Use as Valuation" text-button when `holding.live` (§5), Valuation History (sparkline + reverse-chron list, reusing `dBuildHistorySection`), Linked Liability + Projected Net Position (today and year-20 figures) when a link exists via `findLinkedLiability` — kept from C, which already surfaced this — then Research-prompt-with-copy and Archive as a small actions row at the bottom (§7 on scope). No standalone "Record Valuation" button — inline edit supersedes it.

- *Liabilities root selected (path length 1, Liabilities branch):* total, then a Liability Classes table (name, balance, as-of) — D's `dRenderLiabilityRootView` shape.

- *Liability Class selected (path length 2, Liabilities branch):* class total, then a Liabilities table (name, balance, as-of) — D's `dRenderLiabilityClassView` shape.

- *Liability selected (path length 3):* headline balance (inline-editable, §5), as-of line with staleness note, Valuation History, Amortization Assumptions (rate, original, term, derived + extra payment, projected payoff year, plus the payoff-curve sparkline — dashed, reusing `dSparklineSVG(balSeries, true)`) when `liability.amortization` exists, and — new relative to both C and D — a "Financed Holding" section when `liability.linkedHoldingId` exists that shows **both** the linked Holding's name/value **and** the same Projected Net Position figures (today, year-20) shown on the Holding's side. D only put the Holding name/value here, not the Projected Net Position numbers; C never built the reciprocal side at all. This reciprocity is item (8) of the spec and needs building fresh, not copied.

## 3. Check-in mode

**Entry.** A "Check-in" control lives in the persistent top strip, next to the Net Worth readout, visible regardless of where the columns are drilled. It shows a stale count when >0 (e.g. "Check-in (4)"). Clicking it opens a small two-item menu: "Stale only (N)" (default/first item, bound to plain click on the main label) and "All Holdings (M)" (secondary, reached via a small caret next to the label). This is the one exception to "visit every row" carried from the salvage notes. The item list for a pass is fixed at entry (computed once from `dIsStale`-equivalent over `DATA.assetClasses[].holdings` at the moment Check-in starts) — it does not shrink or reorder mid-pass even if a check-in edit changes a later item's staleness. Liabilities are not part of Check-in, matching the spec's own wording ("a guided pass over Holdings").

**On screen.** The breadcrumb/top-strip row is replaced by a mode strip: "Check-in · stale only" or "Check-in · all", a progress readout pinned right ("12 of 27"), and a persistent one-line key hint ("↵ keep unchanged · L use live estimate · Esc exit"). Below it, in place of the columns and detail column, a single centered card: Holding name, its Asset Class as a subline, the current recorded value in an editable numeric input — auto-focused, existing value pre-selected on mount so typing immediately replaces it — the as-of date, a Live Estimate line with % delta when the Holding is live, and a small history sparkline for context. Nothing else from the column browser is visible while this mode is active.

**Keyboard.**
- **Enter**: commits the input's current value as of today. If the value is unchanged from what was pre-filled (user did not type), this is a no-op — no new Valuation is recorded, per "Enter = unchanged." If it differs, record a new Valuation dated today (same commit path as inline edit, §5, including the settle animation). Either way, advance to the next item.
- **L**: only active when the current Holding has a Live Estimate. Accepts the Live Estimate as the recorded Valuation (same as the "Use as Valuation" action, §5), advances.
- **Esc**: exits Check-in immediately from any point. Any not-yet-committed edit on the current card is discarded; everything already committed earlier in the pass stays recorded. Returns to the Portfolio dashboard (path reset to `[]`).
- Typing digits behaves like any numeric input (pre-selected value means the first keystroke replaces it, not appends).
- No other keys are bound in this mode — specifically not the app's global Left/Right (see §5's note on why those are off-limits) and not Up/Down (there's no list to move through, just one card at a time, advanced only by Enter/L).

**End of pass.** After the last item, the card is replaced by a summary: the Net Worth figure at the moment Check-in was entered (a snapshot taken on entry) vs. the recomputed Net Worth now, and the delta between them, tabular numerals, no color-coding of the sign. A "Done" button (and Enter) returns to the Portfolio dashboard.

## 4. Plan area

Reached as a root-level sibling of "Portfolio" in the top strip (§1) — clicking "Plan" clears the Miller `path`, swaps the entire content region (columns and detail column) for a single scrolling Plan page, and the breadcrumb collapses to the single non-clickable segment "Plan." Clicking "Portfolio" from anywhere, including from inside Plan, returns to the dashboard.

Content, top to bottom, matching the spec's explicit ordering ("above the recorded+projected timeline"):

1. **Target Allocation editor.** One row per Asset Class: name, an editable percent number input (tabular numerals, no unit clutter beyond a trailing "%"), the current actual % shown beside it as static muted text (read from `DERIVED.distribution`, not editable here), and a running total row at the bottom summing the input values live as they're typed. When the total is 100, render it in normal text weight; when it isn't, render it in the same weight but append a plain-text note ("off by 3.0") — no color coding (no red/green anywhere in this app, including here).
2. **Projection assumptions.** Annual growth (%), monthly contribution (money), years — editable number inputs, pre-filled from `DATA.projectionAssumptions`.
3. **Recorded + projected timeline**, read-only, the same visual as the dashboard's (reuse `dBuildTimeline`'s approach) but rendered from a second, independent mount point — it must get its own one-time draw-in the first time the Plan page is opened, not inherit the "already drawn" flag from the dashboard's copy (see §6's note on per-mount draw-in flags), and it should re-render live as the Projection assumption inputs above it change (Target Allocation edits don't feed this chart — only Projection assumptions and Net Worth do).

Both editors update `DATA` in place on `input` (live feedback, not gated on blur/Enter — these aren't "recorded facts" like a Valuation, just planning assumptions), and any change that affects `DERIVED` (Projection assumptions; Target Allocation feeding the dashboard's bars) must trigger `DERIVED = computeDerived(DATA)` again so the dashboard reflects the edit next time it's viewed. Amortization Assumptions are edited on the Liability's own detail column, not here (per the ticket 08 answer — kept explicitly out of Plan).

## 5. Interaction and keyboard spec

**Breadcrumb.** Root segment is either "Portfolio" or "Plan" (§1/§4), always clickable, always returns to `path = []` in that root. Deeper segments (Asset Class name, Holding name, "Liabilities", Liability Class name, Liability name) behave exactly as C's `cBuildBreadcrumb`: click truncates `path` to that segment's depth and re-renders.

**Column click-to-drill.** Clicking a row with children (`hasChildren: true` — Asset Class, "Liabilities", Liability Class) extends `path` by one segment and mounts/replaces every column to its right, exactly as C's `cRerender`. Clicking a leaf row (Holding, Liability) sets it as the terminal path segment and populates the detail column without adding another list column — also unchanged from C.

**Keyboard, column browsing.** Each row keeps C's existing `onActivate` wiring (native `tabIndex`, Enter/Space = the row's click handler), so Tab/Shift+Tab moves focus between rows in native document order and Enter/Space drills or selects. Add Up/Down arrow key handling *within a single column* (move focus to the previous/next row in that same list, wrapping is not necessary) as a plain convenience on top of Tab order — this is new relative to C, which had none. Do **not** bind Left/Right arrow keys to move focus between columns: the app already has a document-level Left/Right handler (index.html, around line 2957) that switches prototype variants, and it only exempts elements inside `[role="tree"]` or form fields. Re-purposing Left/Right for column-to-column focus inside E's columns would either fight that handler or require editing shared switcher code for a marginal navigation gain — skip it. Tab order plus the Up/Down-within-column addition is sufficient and keeps E self-contained.

**Inline click-to-edit Valuation.** Trigger: clicking the detail column's headline figure (Holding's valuation or Liability's balance — the one place a value stands alone at full size). On hover, the headline shows a dotted underline and `cursor: text` to hint it's editable (no pencil/edit icon — the app has no icons beyond chevrons/carets). Click swaps the static text for a numeric text input, pre-filled with the current value, selected on mount. Below the input, a small backdating affordance: muted text reading "for: Today" by default, clickable to reveal a native `<input type="date" max="{DATA.today}">`; picking an earlier date changes what's displayed and is what gets recorded as `recordedAt`.
- **Commit**: Enter, or blur (clicking/tabbing away). Parses the typed number; if it parses, append a new entry to the item's `history` array (`{ date: recordedAt, value }`), set `valuation`/`balance` and `recordedAt` to the (possibly backdated) date, recompute `DERIVED`, close the input, and play the settle animation (§6) on the now-static figure. Every column-1/2/3 row and the dashboard that displays this item's value must reflect the new number on the next render (they will, since they all read from `DATA`/`DERIVED`).
- **Cancel**: Esc while editing reverts to the prior displayed value and closes the input without touching `DATA`.
- **Invalid input**: if it doesn't parse as a number on Enter/blur, don't commit and don't close — leave the input open (no modal, no toast) so the user can correct it.

**Live Estimate "use" action.** A small text-button, "Use as Valuation", directly under the Live Estimate hint line in a Holding's detail (only rendered when `holding.live`). One click commits `liveEstimate` as a new Valuation dated today, through the exact same commit path as inline edit above (history append, `DERIVED` recompute, settle animation) — it does not require opening the inline-edit input first.

**Research prompt with copy.** In a Holding's detail, a small "Research" block: a muted, read-only single line of pre-composed text such as "Look up the current value of {holding.name}. Last recorded {fmtMoney(valuation)} on {fmtDate(recordedAt)}." next to a plain text-button "Copy" (`navigator.clipboard.writeText`). On click, the button label swaps to "Copied" for ~1200ms then reverts — no toast, no icon.

**Archive.** A plain text-button "Archive" alongside Research, in the Holding's (and Liability's) detail actions row. Non-functional (click has no persisted effect) — matching the convention already set for "Add Holding"/"Archive" in the Balance Sheet prototype (ticket 08's answer), kept as scope reduction rather than reinvented here.

## 6. Motion spec

Carry D's timing bands unchanged: ~180–220ms for UI transitions, ~400–600ms for one-time chart draw-ins with stagger, reduced-motion aware throughout (reuse the existing global `@media (prefers-reduced-motion: reduce) { * { transition: none !important; } }` rule and reuse/generalize D's `dReducedMotion()` helper rather than reimplementing it — nothing here needs a different reduced-motion check).

- **New column mounting** (path grows): fade + a small slide in the direction of travel — a horizontal analog of D's "fade + 4px rise" convention, since columns append left-to-right rather than expanding vertically like D's tree did. ~180ms.
- **Detail column content swap** (selection changes at any depth, including entering/leaving the dashboard): fade + 4px rise, 180ms — this one is a direct reuse of D's content-pane treatment, since the detail column is the direct analog of D's single content pane.
- **Row selection highlight** in list columns: keep C's existing flat left-border + `--accent-soft` background treatment (`.c-row.is-selected`), not D's sliding 2px positioned indicator bar — that mechanism (`dRepositionIndicator`, `dAnimateHeight`) exists to track a row's position as the tree scrolls and expands in place; Miller columns don't scroll or expand in place the same way, so it has nothing to track. See §7.
- **Allocation bars**: grow once per mount, 400ms, 40ms stagger per row — reuse `dBuildAllocRow`'s existing once-per-session-flag pattern (`dBarsDrawnOnce`), applied independently to the dashboard's bars and the Asset-Class-view's single bar.
- **Timeline draw-in**: reuse `dBuildTimeline`'s existing sequence as-is (recorded line strokes in over 600ms, projected dashed segment reveals via an animated clip-rect starting after an 850ms delay). Important: the dashboard's timeline and the Plan page's timeline are two separate mount points and must each get their own one-time-draw-in flag — don't let one instance's "already drawn" state suppress the other's first draw-in.
- **Check-in card transition** between items (on Enter/L advancing): fade + 4px rise, 180–220ms, same family as the detail column swap — advancing through Check-in should feel like the same kind of transition as browsing, not a distinct effect.
- **Value-cell settle**, on any committed record (inline edit commit, Live Estimate "Use" action, Check-in Enter-with-a-change or L): a soft one-shot background flash using `--accent-soft` under the figure, fading out over ~400ms ease-out. Applies wherever the new value is first shown to the user (the detail headline, or the Check-in card's value before it advances).
- Nothing loops, nothing bounces, no count-up numbers anywhere — including the Check-in progress counter and the end-of-pass Net Worth delta, which render their final digits directly.

## 7. Deliberately not carried forward

- **D's persistent left sidebar tree.** Explicitly out per the prompt — C's Miller columns are the navigation shape for E.
- **D's sliding selection indicator and expand/collapse height-animation machinery** (`dRepositionIndicator`, `dAnimateHeight`, the chevron-rotate-on-expand interaction). These exist because D's tree expands rows in place inside a single scrolling surface; Miller columns don't expand in place, they navigate by mounting a new column, so there's nothing for a positioned indicator to track and nothing that needs a height transition. C's simpler flat-highlight treatment already does the job.
- **D's "Why this design" panel.** Not requested for E and not part of any of the four spec categories (navigation/information/liability placement/salvage) — it was scaffolding specific to D being a stand-alone proposal that had to explain itself. Skip it; don't invent a replacement.
- **C's original dashboard content**: the Δ-sorted inline-bar table and the single-stroke year-20-only projection line. Both are superseded wholesale by D's tree-ordered allocation bars with money gaps and the joined recorded/projected timeline, per the spec's explicit instruction that information comes from D, not C.
- **C's and D's standalone "Record Valuation" button.** Superseded by the inline click-to-edit headline (§5) — keeping both would mean two different UI paths to the same action.
- **The Balance Sheet shape's list-row inline editing.** The salvage list's inline-edit spec was written for a full-width sheet row with room for a value cell and a date control side by side. In a 220px Miller-column row, a click already means "select/drill," and there's no room for a date affordance — reusing that placement verbatim would create an ambiguous click target. Inline edit is scoped to the detail column's headline figure only (§1, §5).
- **The Balance Sheet shape's value-sorted row order.** Balance Sheet rows sorted by home-currency value descending; E's list columns keep the tree's fixed definition order (matching C and D), so navigating doesn't reshuffle as values change from a Check-in pass or a live edit.
- **The rest of the rejected Balance Sheet chrome** — one-page-is-the-portfolio, non-collapsible sheet sections, the header-band layout, "Sheet · Plan" top-bar tabs. Already discarded in ticket 08's own answer; restated here only for completeness since this brief is meant to stand alone. Plan's access point in E ("Portfolio"/"Plan" as root-level text links in the top strip) intentionally is *not* styled as tabs — no boxes, no tab affordance, just two plain text links, one of which is the current breadcrumb root.

## 8. Revision — reaction to the first render (2026-09-07)

The user's reaction to the built prototype, viewed at a wide (~2000px) window: bigger type, per-asset-class icons, and much better use of horizontal space (dashboard content was capped narrow with ~900px of dead space to its right; Plan and Check-in were similarly stranded left). Three changes followed, superseding the specific numbers given earlier in this brief:

**Type.** Base body size raised from 13px to 15px, with the whole ramp scaled proportionally (11→12, 12→13, 13→15, 18→20, 28→31, 32→36, applied uniformly across CSS, inline JS styles, and the timeline SVG's own text sizes). `.c-col` widened from the 220px stated in §2 to 270px; the detail column's minimum width (§2 said "~440px") is now 560px, both to keep larger type from ellipsizing names that used to fit. List-row and allocation-row heights were bumped (28px→34px rows, 36px→42px allocation rows) so line-height doesn't feel cramped at the new size. `font-variant-numeric: tabular-nums` and the reduced-motion rule are unchanged.

**Icons.** §5 stated "no pencil/edit icon — the app has no icons beyond chevrons/carets," in the context of the inline-edit headline specifically (that part still holds — no edit-pencil icon was added). Read as a general "E has no icons," that line is now superseded: every Asset Class row, Liability Class row, and the top-level "Liabilities" row in the Miller columns, every Target Allocation bar, and the Asset-Class/Liability-Class/Liabilities-root detail headlines now carry a small (16px, single-stroke, `currentColor`, no accent tint) inline-SVG glyph leading the name — real-estate a house, equity a rising line, precious-metal an ingot, cash a banknote, crypto a circled coin, mortgage a house-with-underline, auto-loan a car, credit-card a card rectangle, liabilities (the root row) a falling line as equity's mirror, and any unrecognized class id (the product lets users define custom classes) a plain circle outline as the default/fallback path, not an error. Holdings and Liabilities (the leaf items) still carry no icon, matching §2's row shape otherwise unchanged. Chevrons/carets remain the only other non-text glyphs.

**Space.** `.d-content`'s cap raised from 760px to 1100px outright, and at `min-width: 1200px` the Portfolio dashboard (§2's detail-column content) becomes a two-column CSS grid — Net Worth headline + timeline in a ~1.65fr main column, Target Allocation bars + staleness list + Start Check-in in a ~1fr aside — reaching a 1600px cap at that breakpoint; below it, `.e-dash-grid` has no grid rule and the same DOM order (main, then aside) reproduces the original single-column stack exactly. Plan (§4) gets the same treatment: `.e-plan-wrap` raised to 900px (1400px at the wide breakpoint), with the Target Allocation editor and Projection Assumptions in a 2-column grid at ≥1200px and the timeline full-width beneath, unchanged below the breakpoint. The Check-in card (§3) widened from 420px to 560px and stays centered via its existing flex wrapper. The timeline's SVG (`dBuildTimeline`) had a latent bug exposed by the wider containers: `preserveAspectRatio` was `xMidYMid meet` against a fixed-height/percentage-width box, which letterboxes instead of using extra width once the container's aspect ratio departs from the 720:240 viewBox — changed to `none` (safe here since x and y are already independently scaled via padding/plotW/plotH, not a uniformly-scaled illustration), and the mousemove hover-readout's coordinate math (`W / rect.width`) was already written in a way that's correct under `none` and was actually wrong before under `meet`'s letterboxing. `dSparklineSVG` already used `preserveAspectRatio="none"` and needed no change.

One judgment call: at very deep Miller stacks (three list columns plus the detail panel, i.e. drilling to a specific Liability — `.c-col`×3 + `.c-col-detail` min-width ≈ 1370px) a viewport narrower than that now needs the existing `.c-columns { overflow-x: auto }` horizontal scroll to reach the detail panel, where before widening the same stack needed only ~1100px. This is an inherent tradeoff of the wider columns/detail asked for above, not a regression — content is correct and reachable by scrolling, and on the wide viewports this revision targets there's no scrolling needed at all.
